# CodeStudio-Agent 0.1.0 implementation boundary

Decision: C++26 + XMake; mcpp is a future candidate. Public product name is CodeStudio-Agent; executable/namespace identifiers use codestudio-agent/codestudio.

CodeStudio-Agent owns the headless runtime/harness, CLI, task service, authorization, isolation and scheduling. Desktop UI belongs to the separate CodeStudio Next project, including its UI technology choices. Next can consume the task-service protocol as a trusted client; execution policy, approval validation and recovery remain enforced by Agent.

The application module owns configuration and explicit grants through execute_command. Both the CLI adapter and parent-owned stdio task service call this entry point; the CLI retains terminal presentation, signals and argument encoding. A workspace lock and database lock admit one active runner. The kernel owns the bounded model/tool loop. ToolBroker validates each call before intent persistence and again immediately before execution. Store records action intent and dispatch in durable transactions before effects, followed by result/effect receipts. ModelProvider only proposes operations; it never executes tools directly.

The stdio task service pins one workspace/database at startup, accepts protocol version 2 through structured JSON-RPC requests, and allows one asynchronous operation at a time. The client is trusted to grant tools and cannot change the pinned paths or supply a key through RPC. A bounded writer queue keeps model execution independent of pipe reads; output closure/backpressure and stdin EOF request cancellation. Shutdown joins the operation before reclaiming its transport. Each process has a session ID and retains the newest 64 completed operation receipts, with each result capped at 256 KiB after redaction and explicit omission metadata when larger. Read-only operations/get requires the session and operation IDs; missing receipts never prove absence of effects. Operation IDs are in-memory correlation, not idempotency keys or persistent task IDs. Persisted events carry schema_version 2. The machine-readable contract is protocol/task-service.schema.json; structured errors distinguish rejected requests from unknown command outcomes without guessing from exception messages.

StateReader opens a separate read-only SQLite connection for task summaries, scheduler state and bounded cursor pages. It accepts only state schema 7, never migrates existing state, treats a newly initializing database as temporarily unavailable, and observes only committed events. Other database versions are rejected as a whole; records are not selectively hidden. Event subscriptions poll seq pages; reconnecting clients replay from the last processed seq. Oversized fields are explicitly omitted without skipping records. Provisional text callbacks use the shared credential redactor and separate operation/text notifications, with no durable cursor. No Store insert hook publishes pre-commit events. See task-service.md for limits and the client integration contract.

The runtime has no hidden live model fallback: offline-demo is scripted, and network runs use a user-selected Chat Completions, Responses or Messages endpoint/model. Streaming uses incremental HTTP/SSE parsing and protocol-specific state machines. Only a validated successful terminal response returns tool calls to the kernel. Provisional text callbacks never execute tools. Independent acceptance verification is not yet present.

The credentials module validates explicit env:VARIABLE or system:identifier references, defaulting model runs to env:CODESTUDIO_API_KEY in the application layer. The reference is part of the exact provider binding; secret values are never persisted there. Each task/resume resolves its reference once and pins the value through provider execution and final result/error redaction. No global selected-secret cache or authentication-triggered refresh/replay exists. The original default environment key is also redacted. Model checkpoints without a credential reference are rejected without conversion; database schema 7 and protocol/checkpoint version 2 remain unchanged. Rotation changes the value at the same reference, not task authority or configuration identity.

System storage uses current-user Windows Credential Manager or Linux libsecret/Secret Service. Native operations verify owned target/attribute metadata; missing, locked and unavailable states remain distinct. Linux requires an existing default collection and usable session bus; an operation-wide five-second GCancellable deadline bounds native calls, and a noninteractive SecretService subclass refuses prompt callbacks. No collection creation, unlock, plaintext fallback or cross-user credential discovery is provided. CLI-only credential-set/delete/status manages values, with set accepting bounded redirected stdin and a ten-second input deadline; model-operation RPC options accept references but no raw key or store-management method. The service still has 43 methods. See [credentials.md](credentials.md).

ToolExtension connects frozen external schemas to the same ToolBroker and action ledger. The MCP loader accepts only version 2 of the local configuration manifest, independently of the negotiated MCP date-based protocol version. It validates the whole manifest and explicit server grants before launch or connection. The stdio transport starts persistent direct children with a minimal environment, negotiates the protocol, and exposes only namespaced allowlisted tools. A server's annotations never grant authority. Shared count/byte budgets bound tool catalogs. An observed tool-list change invalidates the connection; malformed results, server errors or lost responses after tool dispatch yield unknown effects and stop the kernel. No automatic restart or replay occurs. A preflight failure before tools/call is sent has no tool effect. Plugin startup is not an audited model tool action; it uses current-user powers in the default none mode or the selected child sandbox.

ProcessRequest and ToolPolicy carry one sandbox mode through ordinary process execution and persistent MCP transport. Windows appcontainer mode uses LPAC, a unique temporary profile/SID per launch and zero capabilities. The profile is deleted after process-tree teardown; Windows also provisions private profile filesystem/registry areas. Only one executable is staged into a private read/execute bin directory; the child can modify a separate low-integrity scratch directory, but cannot write its staging root/bin. No workspace import, script/DLL bundling or scratch export occurs. Both launch paths retain explicit stdio handle inheritance and atomically assign the child to a Job Object at creation. Before execution the host verifies its token, including actual LPAC access-check behavior. Unsupported isolation and setup/launch errors fail without fallback. doctor describes compiled support separately from an actual runtime probe; test evidence belongs in validation.md.

Scratch lasts one ordinary process invocation or one MCP connection. A restarted MCP server receives a fresh scratch and cannot recover its former memory from a host checkpoint. The Job has ActiveProcessLimit=1 with no breakaway, verified before execution; this policy supports single-process stdio tools and binds child_processes:deny and process_limit:1 into checkpoints. This prevents direct descendants in the Job, not every possible external system broker launch. LPAC access still depends on Windows ACLs for system and explicitly permitted resources; this is not a VM or a promise that every read outside scratch fails. The host broker's file tools and provider HTTP are outside child isolation. This ordinary single-process policy is separate from the workspace build extension described below. Linux uses Bubblewrap namespaces, a private root, seccomp and delegated cgroup v2 controls; only native x86-64 ELF system runtime dependencies are staged automatically. Linux ordinary tools also deny descendants and preserve the same checkpoint policy contract. OS disk quotas, complete toolchain packaging and macOS isolation remain future work. See sandbox.md for usage and limits.

models and model-check use the existing HTTP transport but accept only literal loopback addresses, bypass proxies and ignore cloud configuration. The former issues GET /models; the latter makes two model requests with a synthetic function/result. It never dispatches a real tool or creates task state. These commands use CODESTUDIO_API_KEY only with explicit opt-in. Capability success is a simple protocol smoke test, not a guarantee of coding quality or broad model compatibility.

The normalized assistant history carries private provider continuation fields for Responses output items and Messages content blocks; each adapter reconstructs only its own wire format. Responses uses stateless full-history requests with store=false. Protocol errors, malformed/truncated tool arguments and missing terminal events fail before action preparation. CLI redacts keys across delta boundaries before printing provisional text to stderr; stdout remains the final JSON receipt.

Action execution status and effect status are distinct. A successful process receipt proves exit code zero and bounded completion, not that arbitrary external business actions succeeded. A failed/terminated process may have effects and is marked unknown. Prepared/dispatched actions prevent normal task finalization until resolved; recover records interrupted state without executing anything.

Persistent records use schema version 7. Both readers and writers reject other database versions without migration; callers must use a new state database or workspace to create tasks. Checkpoint envelopes, bindings and kernel states use version 2 exclusively. A checkpoint stores conversation, native provider continuation, pending tool calls, cursor, consumed model attempts and the immutable execution binding. Tool result/denial and checkpoint advancement are atomic; the final answer checkpoint and task finish are also atomic. Resume checks a matching workspace, provider/configuration, policy and schemas with newly supplied grants, then reuses receipts without replaying completed effects. Foreground running tasks require explicit recover first; unknown/partial effects and incompatible or redacted checkpoints cannot resume. Total request budget stays bounded across resumes. The scheduler reconciles its own interrupted jobs after a worker restart; explicit bounded supervision can trigger that restart without changing task recovery authority.

The application scheduler accepts explicit resume enrollment for existing paused tasks and cron templates for recurring fresh tasks. Resume enrollment persists the original grants as bounded credential-free arguments, exact binding, checkpoint revision, unchanged cumulative model budget, deadlines and attempt limits. One database admits at most 100 active jobs and one active job per task. The worker uses separate workspace/database scheduler ownership locks, acquires ordinary runner locks only for execution, and runs one job at a time. Only one worker owns a database, and it executes jobs matching its pinned workspace binding. Shared-database workspaces require stopping that worker and starting one for the desired workspace. Owner generation, claim token and expected checkpoint revision fence every claim; task outcomes and corresponding job transitions commit together. Safe model_pending failures may retry with bounded exponential backoff. Uncertain effects and binding/revision changes block the job. Successful manual resume cancels the prior enrollment in its transaction. New build proposals always wait for a new explicit decision; neither stored resume grants nor retries authorize approval.

Cron enrollment freezes the prompt, model configuration, explicit grants, tool schemas and an initial ready checkpoint without a model request. Authorized MCP discovery can run at enrollment, so the service exposes crons/create as an asynchronous operation; other cron controls remain synchronous. Each occurrence creates its task, fresh checkpoint, scheduler job and unique (cron_id, scheduled_at_ms) receipt in one transaction. Conversation and max_turns start fresh while the workspace retains its current files. Per-occurrence retries keep that occurrence's cumulative budget. Missed idle periods coalesce to the latest due instant; slots during a queued, running or approval-waiting occurrence are skipped without consuming max_runs. Job completion and next_due advancement commit together to prevent an active period becoming a delayed replay. Manual takeover retains the same non-overlap constraint. A blocked job or uncertain outcome pauses future occurrences and cannot be bypassed by resuming the series.

The cron time module accepts five numeric fields, wildcard/list/range/step syntax and Sunday 0 or 7. Restricted day-of-month/day-of-week fields use OR; * and */1 are unrestricted while larger steps remain restricted. UTC does not require a time-zone database. local resolves once to the system IANA name at enrollment, and explicit IANA names use std::chrono time-zone data. DST gaps produce no occurrence; fold instants are compared in UTC order, including non-hour offset transitions. Searches are bounded to approximately eight years and UTC years 1601..9999. Preview exposes UTC milliseconds and local/UTC display strings without creating state.

Windows scheduler-start uses an independent hidden process with only NUL handles inherited; it verifies the suspended child has escaped parent Jobs before execution and fails closed otherwise. Client EOF/shutdown affects the foreground service operation, not a successfully detached worker. The persisted queue stores credential references only. Each worker task/resume reads the referenced system value afresh; an active operation keeps its original value. Environment references still read the startup environment, so those keys require restarting from an updated environment. scheduler-stop cancels the active job and preserves other queued work. Scheduler control state, PID and heartbeat are last registered metadata and may be stale after a crash; they are not liveness certification or authority to kill a PID. Recovery reuses durable receipts for owned jobs, marks dispatched actions unknown, and does not recover unrelated foreground tasks. Linux scheduler-start uses double fork, setsid, an exec receipt pipe and /dev/null standard handles. Its exec boundary closes inherited descriptors and preserves the startup environment. Linux autostart registers an exact owned systemd user unit plus enable link for user-manager startup; it never enables linger or starts the worker during registration. Session/cgroup cleanup can still terminate detached workers. See linux.md and scheduler.md.

Opt-in scheduler-supervise, or scheduler-start --supervise, owns one child worker at a time. Workspace/database admission locks cover both execution and backoff; ordinary workers also take these locks. The internal scheduler-child keeps the original worker locks and atomically compares the expected stop_epoch and previous generation when registering. A stop committed during launch therefore rejects the stale child. An OS process handle or waitpid proves exit; only abnormal exit after registration can trigger a bounded replacement with exponential backoff. Normal exit, cancellation, ownership change and lifetime restart exhaustion end supervision. The Windows child belongs to a kill-on-close Job at CreateProcess time through JOB_LIST; Linux uses PDEATHSIG and validates the parent after fork. The supervisor must reap its owned child before another launch. No recorded PID is reopened for cleanup. Task grants, deadlines, action receipts and budgets remain authoritative; unknown effects still block continuation. Supervision settings, lifecycle phase, restart count, last observed child exit, next restart time and terminal reason are durable. Platform autostart defaults to an ordinary worker and accepts explicit bounded supervision; the supervisor itself is not restarted.

State schema 7 adds supervisor_runs and an independent supervisor_events sequence. Lifecycle transitions and their events commit atomically; heartbeat updates do not append events. A new admitted run closes the previous nonterminal record with reason superseded, retaining its nullable last child exit without manufacturing an exit observation. Schema 6 and all other initialized database versions are rejected without migration. Process death or failed persistence may leave the latest record in a nonterminal phase. Neither supersession nor historical phase grants process-control or task-replay authority.

scheduler/status adds a supervisor object, also available directly through scheduler/supervisor/status. It combines the latest durable record, worker_matches and a separate observation with state and observed_at_ms. Worker and supervisor records come from one committed database snapshot; worker_matches only compares owner/generation. The later OS observation is not atomic with that snapshot. Windows reads creation FILETIME and exit state through the same read-only handle; Linux compares boot ID and starttime while a pidfd brackets the proc read with exit checks. Inconclusive or unsupported observation is unavailable; matching_process only establishes identity at that instant, never health or future liveness. not_running and identity_mismatch cannot authorize cleanup through a stored PID. With no record the observation is not_checked. A stopped receipt may briefly coexist with a still-matching supervisor process because persistence precedes process exit. scheduler/supervisor/events returns bounded 1..100-item cursor pages; its seq is separate from task event subscriptions. CLI commands provide the same read-only views. The service advertises supervisor_diagnostics on Windows/Linux; its 35-method machine contract remains protocol version 2.

Windows login autostart is a separate, explicitly enabled Task Scheduler registration tied to the current user SID, workspace and database. It uses an interactive token at ordinary privilege, stores no password or API key, and directly invokes the fixed executable with scheduler-run and absolute workspace/state arguments by default. scheduler-autostart-enable --supervise instead fixes scheduler-supervise and its bounded restart options in the registration. Registration does not immediately invoke Run or bypass parent-Job restrictions. Enable and disable verify the complete owned execution contract before changing an existing entry; conflicts are not overwritten. Disable removes future login launches without stopping a live worker or supervisor. Task Scheduler Hidden hides the registration, not necessarily the process console window. Login-launched processes inherit the login environment, not a previous terminal's temporary credentials. Tasks bound to system references use the same user's credential store when it is available in that login session. No pre-login system service is installed. See [scheduler.md](scheduler.md).

The shared AutostartOptions model fixes poll_ms, supervise, max_restarts and restart_delay_ms. Both backends bind ordinary and supervised modes to the same user/workspace/database identity. Enable requires the exact requested execution contract; switching modes or limits requires disable followed by enable. Status and disable infer stored options only after strict validation and full native-contract reconstruction. Returned supervised is always present; restart limits appear only when true, and removal receipts retain the removed configuration. Absent or conflicting registrations do not make requested/default options evidence of ownership. Windows restart_count remains zero and Linux Restart=no in both modes, so the OS cannot renew a supervisor's exhausted lifetime budget by restarting it. A later login or user-manager-start trigger can start a new supervisor lifetime while durable task authority, budgets and deadlines remain unchanged. The stdio service exposes supervised_autostart and the same explicit options on scheduler/autostart/enable; its status/disable methods need no mode options.

Known-key redaction that changes checkpoint state or binding disables future resume rather than replaying altered native signatures or call arguments. Credentials are resolved anew at operation boundaries; stored conversations remain plaintext. System-store protection does not restrict an authorized unisolated process running as the same user from calling OS credential APIs, nor does choosing an arbitrary environment reference automatically strip that variable from every child. Files are UTF-8 text with bounded size; writes use a temporary file and replacement after identity checks. Resume does not roll back workspace edits or pin executable bytes. Its binding records the sandbox policy version/mode/filesystem/network contract. Switching modes fails before MCP startup. Untrusted concurrent same-user mutation and default-none privileged shell execution remain beyond the isolation boundary.

Tests must verify behavior in release as well as debug; assertions must remain active under NDEBUG. Synthetic providers and local HTTP fixtures exercise the real parser, kernel, tools and database. The standalone CLI crash test verifies persisted dispatched intent survives termination and requires explicit reconciliation.

WorkspaceBuild is a thin, frozen ToolExtension with the single parameterless build_workspace tool. It snapshots the manifest, normalizes its versioned explicit steps, passes the resulting data through host validation, and rechecks the manifest before execution. CLI build, model tools and the task service retain this shared entry point and the same action ledger. The extension does not own Windows process setup or construct tool-specific commands.

BuildProposal is a separate opt-in ToolExtension exposing only propose_build. It validates a model-supplied v2 manifest and freezes its explicit steps without importing files, launching processes or exporting artifacts. The version-2 tool receipt has effect none and contains the manifest, recipe, workspace, host-protected paths and a SHA256 digest of the canonical JSON representation. It has no plugin marker. This digest identifies configuration, not a historical snapshot of source or compiler bytes. The grant participates in the resume binding and the tool shares the extension catalog budget with fixed builds and MCP.

The application layer owns review/approve/reject through CLI and trusted stdio methods; these methods are not model tools. Review uses StateReader and never creates or migrates a database. Before a decision the application reconstructs the proposal and requires both exact receipt equality and the caller-supplied digest. The state schema includes a unique build_proposal_decisions record for each source action. Approval inserts that record, a separate approved-build task, its prepared action and audit events in one transaction. Only a newly committed decision can dispatch. Execution uses WorkspaceExecution directly and persists the same action/effect receipts as other harness tools. It retains the source proposal's protected paths and adds the current database paths. Repeated decisions return the original task; conflicting decisions fail. Crash recovery preserves the decision and resolves prepared/dispatched actions without releasing them for retry. Approval tasks have no conversational checkpoint and cannot resume; a further build attempt requires a new proposal. A successful propose_build pauses the source task as waiting_approval with the original tool call unanswered. Explicit resume recomputes SHA256 over the entire saved proposal output excluding digest, checks the proposal and decision digests, validates the settled build receipt, then appends one result for that call. Newly produced continuation feedback must remain unchanged under current-key redaction; otherwise the application refuses continuation before provider construction or MCP startup. The checkpoint cursor advance and build.proposal.consumed event commit together; the original proposal receipt remains immutable. Pending decisions, running builds and unknown effects block continuation.

The application also supports explicit approval continuation through CLI --continue-task or service continue_options. It reuses the normal resume authorization and configuration path, and keeps the source task ID and saved cumulative model budget unchanged; raising the budget requires a separate explicit resume. Default approval itself makes no model call, but new approved execution requires resolving the source task's saved credential reference before receipt persistence so its selected key can be redacted. Reject-only remains possible without an available key. Combined approval/continuation pins the same resolved value across both phases; a separately enrolled worker resolves its own operation value when it observes the settled decision and continues. Combined operations require the source task to still wait on the exact proposal; cancellation and repeated requests cannot advance later work. An already-cancelled execution also skips combined continuation. A source still waiting on the exact proposal may continue even if its decision was committed by an earlier request. A later continuation failure does not roll back the committed decision, execution receipt or exported artifacts. The response preserves the decision structure and adds a continuation status/result or reason/error. The service exposes approval_continuation:true, automatic_resume:true and background_scheduler:true. Foreground approval continuation and durable scheduler enrollment remain separate explicit requests. See build-proposals.md.

normalize_build_manifest is an ordinary host module accepting a version-2 manifest and producing a version-2 generic execution recipe without version conversion. It never generates tool-specific commands, environment defaults or allowlists. Product documentation describes generic explicit execution plans; XMake configuration/build commands and private cache environment live only in the [regression fixture](../tests/fixtures/xmake-build/). The project itself still builds with XMake. MCP remains an independent tool-extension mechanism, with no external MCP-to-host execution interface.

Only manifest version 2 is accepted. It requires explicit steps and declares all required tool-specific environment values. Build bindings and proposal receipts use version 2 without a plugin field. The execution backend is identified as windows-lpac-build-v2 on Windows and linux-namespace-build-v2 on Linux. A changed recipe or binding blocks resume. Other tools such as CMake or Cargo are not validated merely because the recipe format can represent their commands.

WorkspaceExecution owns the generic host execution implementation in src/execution. Its constructor validates and copies the recipe without launching anything; callers must authorize and persist intent before execute. It has no plugin, model or tool-schema dependency. The host accepts at most 64 explicit uppercase environment names, retains system/home/temp names, rejects common credential and proxy names, and expands only declared private roots. Values remain plaintext; name filtering is not secret detection. WorkspaceExecution stages declared sources into a private writable tree and explicit toolchain/dependency inputs into private read-only trees, then executes fixed steps in an LPAC session on Windows or a Bubblewrap/seccomp/cgroup v2 session on Linux. Linux copies ELF system runtime dependencies into the private root and never mounts the host toolchain implicitly. Build sessions have exactly registryRead (required for native Windows descendant creation), no network capabilities, an atomically assigned Job with process/memory/CPU limits, and a total cancellation/deadline budget. Each step drains its complete Job before the next step or export. A narrowly scoped path projection avoids LLVM traversing protected host ancestors without changing source or parent-directory ACLs.

BuildWorkspace IO anchors source/target ancestors, rejects reparse points, hardlinks, unsafe components and short-name aliases, copies bytes without source ACLs and computes SHA256 in the host. Outputs are published only into a unique new bundle through same-volume rename; receipt slots are allocated before publication. Before export failures have no published artifact effect; successful export is applied. The normal dispatched-action crash rule remains unknown and blocks replay. Build configuration participates in exact resume binding, and build/MCP schemas share a pre-launch catalog budget. The direct build command uses a scripted isolated-build provider, so it follows the same ledger and continuation rules without model access. See workspace-builds.md.

## Remote MCP transport

McpPlan owns exact manifest bytes and parsed endpoint/grant/credential pairs. Static validation completes before connecting; all granted credential references resolve before any process or network operation. The application pins remote credentials separately from model selection, checks saved bindings before connect, and installs every secret in stream, result and approval redaction. Reflected credentials in discovered schemas are rejected. The protocol layer owns RPC correlation, catalog validation and effect receipts; stdio and native HTTP transports own framing, deadlines and resource lifetime.

Streamable HTTP supports JSON and SSE with session/version headers. The only response recovery is bounded GET with a committed event cursor, never a repeated POST. Session expiry invalidates the extension; an explicit new load initializes and discovers again. Cancellation sends a best-effort protocol notification, but dispatched unknown effects stop continuation. HTTPS certificate validation and disabled redirects bind credentials to the configured endpoint. Local process sandbox requests cannot be fulfilled by a remote service and are rejected. See [MCP boundaries](mcp.md) for limits and platform details.


## Isolated process packages

PluginPlan translates its frozen payload inventory and argument templates into an immutable ProcessPackage. The platform module accepts this generic plan without interpreting plugin format or version locks. It imports exact files into owned storage, checks hashes/sizes/executable modes, and exposes only that copy to the child; platform-specific libraries and process resource limits remain behind WindowsSandbox/LinuxSandbox. A package never authorizes itself: limits are host MCP configuration and are bound alongside the lock as isolated-process-package execution semantics. Ordinary command policy remains separate. See [plugin-sandbox.md](plugin-sandbox.md).
