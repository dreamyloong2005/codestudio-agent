# Durable resume implementation contract

The runtime supports explicit `resume <task-id>` and separately authorized durable resume enrollment. An independent scheduler worker processes enrolled tasks; automatic worker relaunch is not provided. C++26/XMake remain fixed; local-model work is paused.

Persistent state uses schema 7 exclusively. Readers and writers reject any other initialized database version before changing its settings; no migration or per-task history filter is provided. Use a new state database or workspace and create new tasks. `Store::checkpoint` returns `{"version":2,"state":object,"binding":object}`. The envelope, state and binding each require version 2. Checkpoint JSON has a 16MiB serialization limit.

Kernel state version 2 contains `messages` (full normalized history including native continuation), `pending_calls` (array of id/name/arguments), `next_call` (cursor), `turns` (model attempts already spent), `max_turns`, `tool_failed`, `calls_seen` (IDs), `phase` (`ready`, `model_pending`, `tools`, `finished`), `resumable` and `blocked_reason`. Before each request, persist model_pending and increment turns. Resume of model_pending may issue another model request within the total budget; it cannot dispatch an unrecorded model response. Persist validated assistant reply plus pending calls before effects. Completed tool result and updated checkpoint are one transaction; same for denials. A final answer and finished phase are committed together.

State persisted through the kernel is known-key redacted. If redaction changes any checkpoint content or binding, set resumable=false with a generic reason; never resume altered signed continuation, arguments or IDs. The current in-memory run may continue. No API key or credential environment is stored. Database and conversation are otherwise unencrypted.

Binding contains `version:2`, `provider` (ModelProvider name), `workspace`, `policy` (canonical executable/protected paths, write grant and file/process limits), `tools` (frozen schemas), `configuration` (RunOptions.binding). Configuration is supplied by CLI and includes nonsecret provider config and version-2 local MCP config. This local configuration version is independent of the external MCP date-based protocol version. All bindings must compare equal on resume. CLI restores provider defaults from the saved config but requires explicit write/process/MCP and insecure-loopback grants again. Secrets come from current environment only. No model/endpoint switching during resume.

Sandbox policy is explicit under `policy.sandbox`. The unisolated mode is `{"version":2,"mode":"none"}`. AppContainer uses `{"version":2,"mode":"appcontainer","network":"none","filesystem":"private-scratch","child_processes":"deny","process_limit":1}`. The last two fields bind a single-active-process Job with no breakaway, denying direct descendants. CLI defaults to none; resuming an appcontainer task requires the original `--sandbox appcontainer`. Any mode or version change fails exact policy comparison before MCP starts. Unsupported modes fail before Store creation or process launch.

Sandbox state is not checkpoint state. Each ordinary invocation gets fresh scratch; each MCP connection keeps scratch only for that connection. Restarting or resuming an MCP server creates a fresh SID and scratch, with no plugin memory/temp-file recovery and no automatic workspace export. The checkpoint binds the isolation contract, not a transient SID/path. Previously receipted calls still never replay simply because a plugin lost its private state.

Eligible task states are interrupted, cancelled, failed, exhausted or waiting_approval. The waiting_approval state requires the exact pending proposal decision and a settled approved execution with known effects, or an explicit rejection. completed and needs_attention are not resumable. Running tasks require explicit recover first. Reject unknown/partial/dispatched/prepared effects, missing/incompatible checkpoints, redacted checkpoints, or invalid state before any model call. `recover` marks dispatched as unknown and prepared as not_executed as before. A pending call with a not_executed receipt is skipped with a synthetic failure result; an unprepared pending call can execute after current authorization. Any completed ledger row matching a pending cursor must match saved ID/name/arguments and supply the existing result, never rerun. Duplicate call IDs remain rejected across resumed turns. Remaining tool failures carry into the final needs_attention status.

Store helpers: save_checkpoint(task,state,binding) upserts while running and forbids binding changes; checkpoint(task) reads the envelope; finish_action/deny_action/finish_task accept optional checkpoint state and persist it in their existing transaction; resume_task(task,expected_binding) transactionally validates allowed task/checkpoint/effect state and exact binding then records task.resumed and switches to running. Existing function calls without checkpoints remain supported. Store validates minimal checkpoint envelope fields and kernel deeply validates messages/cursors/calls before resume_task.

Max turns is a total model request budget (1..100). Resume defaults to the saved max_turns; exhaustion requires an explicit larger --max-turns. A resumed task keeps its task ID and action ledger. CLI show should include a bounded checkpoint summary, not duplicate the whole history; internal checkpoint is read via Store API.

The optional propose_build grant is part of configuration as build_proposals version 2 with explicit-digest approval. A successful proposal keeps its immutable receipt but leaves the original tool call unanswered and the checkpoint cursor on that call. The task pauses as waiting_approval, emits task.waiting_approval and returns exit code 3. Resume must repeat --allow-build-proposals and all original grants. Pending decisions, running approved builds and unknown/partial effects cannot continue. Approved builds run as separate approved-build tasks without conversational checkpoints; recovery preserves the unique decision and never replays an approved action.

Before continuation, Store recomputes SHA256 over the complete saved proposal output with only digest removed, using the same canonical JSON dump, and compares it with both the proposal and decision digests. An unchanged digest string does not allow changed proposal content. Once the decision and any execution receipt are settled, resume builds one tool result for the original call containing proposal, decision and execution. It does not alter the proposal receipt or call the build tool again. The new tool message, one-step checkpoint cursor advance and build.proposal.consumed event commit atomically. Repeated resumes must not duplicate the consumed result. This result has effect none for delivering the decision; any approved build effect remains in its separate execution receipt. Execution feedback may have been created after the saved checkpoint. The application checks the complete new continuation result against the current CODESTUDIO_API_KEY redactor before constructing the provider or starting MCP. If redaction would change that result, resume refuses it rather than injecting altered feedback.

CLI build-approve/build-reject accept an explicit --continue-task with the original resume grants/options; RPC builds/approve/builds/reject accept continue_options. The default decision operation itself performs no model request; a separately enrolled worker may observe the settled decision and resume. Combined execution starts only while the source task still waits on the exact reviewed proposal; repeated decisions must not advance a later checkpoint or a different pending proposal. A cancelled request or already-cancelled approved execution skips combined continuation. A repeated decision can still continue a source that has not advanced and still waits on that exact proposal. The committed decision, execution receipt and any published artifacts survive a later continuation failure; outer failure must not be interpreted as no execution. The returned decision structure is preserved, with normal credential redaction for display, and gains continuation with status started (result and exit_code), skipped (reason), or failed (error). Combined continuation requires the saved cumulative model budget unchanged; callers must use separate explicit resume to increase it. A started continuation supplies the outer exit code; a failed continuation returns 2 (130 on cancellation), while a skipped continuation preserves the decision exit code unless cancelled. The service advertises approval_continuation:true, automatic_resume:true and background_scheduler:true; background grants require a separate schedules/create request. See build-proposals.md for the host approval protocol.

Scheduler enrollment persists only the original explicitly repeated resume grants, exact binding, checkpoint revision and unchanged cumulative model budget. It admits at most 100 active jobs and one active job per task. Attempts and deadlines bound safe model_pending retries; new proposals always require a new decision. A scheduled claim is fenced by worker owner/generation, claim token and checkpoint revision; normal runner locks prevent concurrent manual and scheduled execution. Successful manual resume cancels the previous enrollment transactionally. Task outcomes and job transitions commit atomically. New workers may reconcile their own interrupted jobs and reuse completed receipts, but unknown effects block continuation and unrelated foreground crashes still require explicit recover.

The independent Windows/Linux worker survives stdio EOF and inherits credentials from its startup environment. Credentials are not stored in queue arguments or bindings; key rotation requires restarting the worker from an updated environment. scheduler-stop cancels the active job and preserves other queued work. The control record is last registered state, not a liveness guarantee. Windows startup fails if the child cannot escape parent Jobs; stored PIDs must not be used as authority to terminate processes. Linux uses double fork, setsid and an exec receipt with closed inherited descriptors. Windows current-user login registration and Linux systemd user-manager-start registration are explicit, do not launch immediately and do not save credentials. There is no automatic crash restart or pre-login system service. Existing Linux session and linger policy still governs the manager lifetime. See [scheduler.md](scheduler.md) for CLI/RPC contracts and lifecycle limits.

Build manifests and execution recipes use the same version-2 format without version conversion. Build bindings and proposal receipts use version 2 without a plugin marker; the Windows backend identity is windows-lpac-build-v2. A saved build grant must match the explicitly supplied manifest, recipe and backend before resume. Proposal validation recomputes the complete version-2 receipt and requires an exact digest match before a decision.
